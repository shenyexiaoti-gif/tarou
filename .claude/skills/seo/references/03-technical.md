## 1. 6層モデル

テクニカルSEOは **クロール → インデックス → レンダリング → 構造 → ページ体験 → 構造化データ** の6層。
**必ず上の層から潰す。** クロールされていないページの表示速度を直しても意味がない。

## 2. クロール

**確認**
- `robots.txt`：意図せず重要ディレクトリをDisallowしていないか。CSS/JSをブロックしていないか（レンダリングできなくなる）
- XMLサイトマップ：正規URLのみ、200を返すURLのみ、`lastmod`が正確、robots.txtから参照、GSCに送信済み
- GSCの「クロールの統計情報」：リクエスト数の推移、レスポンスコード内訳、平均応答時間
- サーバーログ：どのURLにクローラが何回来ているか（大規模サイトでは必須）

**クロールバジェットが問題になるのは主に大規模サイト**（数万〜数十万URL）。中小規模で気にしすぎない。ただし以下は規模を問わず害になる:
- パラメータ違いの無限URL生成（絞り込み、並び替え、セッションID）
- ページネーションの無限ループ、カレンダーの永久リンク
- ソフト404の大量発生
- 極端に遅いレスポンス（クロール頻度が落ちる）

**対処**：不要URLはrobots.txtでクロール抑制／リンクを張らない、正規化を明確化、内部リンクからのリンク切れを解消。

## 3. インデックス

**インデックスされない主因（頻度順）**
1. `noindex` が残っている（テスト環境の設定が本番に出る事故が最多）
2. robots.txtでブロック（※ブロックされるとnoindexも読まれない。**noindexを効かせたいならクロールは許可する**）
3. canonicalが別URLを指している
4. 重複・低品質と判断された（「検出 - インデックス未登録」「クロール済み - インデックス未登録」）
5. サイトが新しく、評価が溜まっていない
6. 認証・IP制限・ステータスコードの誤り（soft 404、意図しない5xx）

**正規化（canonical）の原則**
- 全ページに自己参照canonicalを入れる
- httpとhttps、wwwあり／なし、末尾スラッシュ有無、index.html有無を1つに統一しリダイレクト
- パラメータ付きURLは正規URLを指す
- canonicalは**ヒントであって命令ではない**。矛盾するシグナル（サイトマップ、内部リンク、リダイレクト）を揃える

**リダイレクト**
- 恒久移転は301。一時的は302。JSリダイレクトは避ける
- リダイレクトチェーンは2ホップ以内、ループは即修正
- サイト移行時は**旧URL→新URLの1対1マッピング**。全部トップに飛ばすのは評価を捨てる行為

**ステータスコード**：存在しないページは404か410を正しく返す。200で「見つかりません」と表示するソフト404を作らない。

## 4. レンダリング（JavaScript SEO）

- Googleはレンダリングするが、**即時ではなく遅延することがある**。重要コンテンツをクライアントサイドJS依存にしない
- SSR / SSG / 動的レンダリングのいずれかで、**初期HTMLに本文・見出し・内部リンク・メタ情報を含める**
- リンクは `<a href="...">` で書く。onclickだけのナビゲーションは辿られない
- 無限スクロールはページネーションURLを併設する
- 検証：GSCのURL検査「レンダリング済みHTML」／`curl` で生HTMLを確認して本文の有無を見る
- **AIクローラーの多くはJavaScriptを実行しない**。GEO観点でもSSRが有利（→ `06-ai-search-geo.md`）

## 5. サイト構造・URL・内部リンク

**構造**
- トップから重要ページまで**3クリック以内**を目安
- ディレクトリはトピック単位で切る（`/seo/technical/` のように意味を持たせる）
- パンくずリストを設置し、BreadcrumbList構造化データを付ける

**URL**
- 短く、意味が分かり、階層が浅い。日本語URLは可（エンコードされる）だが英字の方が扱いやすい
- 公開後は変えない。変えるなら必ず301

**内部リンク（最も費用対効果が高い施策の一つ）**
- 重要ページほど多くの内部リンクを受ける設計にする
- **アンカーテキストは具体的に**。「こちら」「詳しくはこちら」を減らし、リンク先の内容を表す語にする
- 新規記事を公開したら、**既存の関連記事から必ずリンクを追加する**（公開時のルーチンにする）
- 孤立ページ（内部リンクを1本も受けていないページ）をゼロにする
- フッターに全ページを並べる等の機械的な大量リンクは効果が薄い
- 外部リンクは出し惜しみしない。良質な出典へのリンクは信頼性のシグナル

## 6. ページ体験（Core Web Vitals）

**指標（2026年8月時点。閾値と指標構成は変わるので実装前に必ず最新を確認）**

| 指標 | 意味 | 良好の目安 |
|---|---|---|
| LCP | 主要コンテンツの表示完了 | 2.5秒以内 |
| INP | 操作への応答性（旧FIDの後継） | 200ms以内 |
| CLS | レイアウトのずれ | 0.1未満 |

**評価は実ユーザーデータ（CrUX＝フィールドデータ）**。Lighthouseのラボスコアは診断用であって評価対象ではない。**GSCの「ウェブに関する主な指標」レポートを正とする。**

**改善の定番**
- LCP：画像の最適化（WebP/AVIF、適切なサイズ、`fetchpriority="high"`）、サーバー応答（TTFB）短縮、CDN、レンダリングブロックするCSS/JSの削減、Webフォントの最適化
- INP：長いタスクの分割、不要なサードパーティスクリプト（タグ、チャット、広告）の削減・遅延読み込み、イベントハンドラの軽量化
- CLS：画像・動画・広告枠に**width/heightまたはaspect-ratioを指定**、フォントの `font-display: swap` とフォールバック指定、後から挿入される要素の領域確保

**位置づけ:** CWVは**同程度の品質のページ間での差を分ける要素**。コンテンツの弱さを速度で埋めることはできない。ただし極端に遅いサイトは離脱で確実に損をする。

## 7. モバイル・多言語・国際化

- **モバイルファーストインデックス**：評価はモバイル版が基準。PC版にしか無いコンテンツは存在しないのと同じ
- タップ領域、文字サイズ、横スクロール、インタースティシャル（画面を覆う広告・ポップアップ）に注意
- 多言語：`hreflang` を相互に正しく指定（自己参照も含む）、`x-default` を用意。言語ごとにURLを分ける（同一URLでの自動切り替えは避ける）
- 地域ターゲティング：ccTLD / サブディレクトリ / サブドメイン。**運用しやすいのはサブディレクトリ**
- 機械翻訳をそのまま公開しない（品質が低ければスパム判定の対象になり得る）

## 8. よくある事故と一次対応

| 症状 | 最初に見るところ |
|---|---|
| 全ページが急に圏外 | robots.txt、`noindex`、サーバーの5xx、DNS、SSL証明書切れ、手動対策 |
| 一部ページだけ消えた | canonical、重複、リダイレクト設定、削除・URL変更 |
| インデックス数が急減 | GSCのインデックス作成レポートの除外理由を分類して原因を特定 |
| リニューアル後に激減 | URLマッピング漏れ、リダイレクト不足、テスト環境設定の本番混入、内部リンクの断絶 |
| 検索結果のタイトルが変 | 内容との乖離、キーワード詰め込み、テンプレの重複 |

**サイトリニューアル／ドメイン移行の前に必ずやること:** 旧URL全件のリスト化 → 新URLへの1対1マッピング → 301設定 → サイトマップ差し替え → GSCのアドレス変更ツール → 移行後2週間は毎日インデックスとエラーを監視。
